# Implementation Map

**What exists right now, and what to know before building on it.**

This file describes the **current state** of the codebase, so a developer (or AI agent) starting a new story can see what to reuse and what to watch out for. It is edited in place: when something changes, update or remove the entry.

- Which stories are done: the Product backlog sheet. How a story was built and verified: its PR description (before 2026-11-01, `docs/BUILD_LOG.md` §4, now frozen).
- For *what the system should do*, see `docs/REQUIREMENTS.md`.

**Update this file when you add or change an endpoint, a reusable piece, a table, or a contract another story relies on** (root `AGENTS.md`, "Keep the paper trail current"). Put a new row **next to related rows** (same module or path), not at the end of a table, so two open PRs rarely edit the same lines. There is no status table and no "last updated" line: the backlog, open PRs and git history hold those.

### SCRUM-86 waitlist endpoints

The existing registration endpoints above are extended by SCRUM-86: full, enabled events create `waitlisted` rows in FIFO order; `GET /registrations/me` includes `invited` rows and their `invitation_expires_at`. `POST /registrations/{registration_id}/accept` accepts only the caller's active, unexpired invitation. `DELETE /registrations/{registration_id}` removes the caller's `waitlisted` row or cancels an `invited` reservation. All three are active-Attendee-only; identity comes from the verified session. Database occupancy counts Registered rows plus unexpired invitations, not queue entries.

`modules/notifications/` serves the bell. These endpoints have no role gate on purpose: every role has a bell, and each call is scoped to the caller's own rows in the active role. `tests/test_active_role_access.py` therefore lists `/notifications` as open, like `/auth`; `TestActiveRoleDenial` in `test_notifications_api.py` proves the scoping with a user who holds a second role.

`modules/equipment/` holds equipment availability (SCRUM-23), the tech-support dashboard reads (SCRUM-73) and request lines (SCRUM-45). Build equipment work inside it rather than creating a new top-level module. `/equipment/catalogue` and `/equipment/requests*` are declared **above** the parameterised `/requests/event/{event_id}`.

## 5. Know before you build

- **Check the live schema, not only `supabase/migrations/`.** Migrations have reached the shared project before their PR merged (D67), and remote-only migrations have appeared in the ledger. Run `supabase migration list --linked` and the Supabase advisors before relying on the files.
- **Change and cancellation requests (stories 84, 115):** build SCRUM-32/37 on `event_change_requests`, not a new table. A cancellation request supersedes an open change request (CR-R1, done in `request_event_cancellation`), and story 32 refuses a change request while a cancellation is open (CR-R14): one open request per event. Story 115 records decisions on the request row (`status`, `decided_by`, `decided_at`, `decision_reason`); an approval leaves `decision_reason` null and puts the organiser's reason in the status history instead. Anything else that cancels an event (for example CAL-R6's "no replacement venue") should go through `cancel_event`, so the releases and notices stay in one place. Event reads call `get_open_cancellation_request`, `list_cancellation_requests` and (dashboard) `list_open_cancellation_requests`; `tests/conftest.py::cancellation_requests_offline` defaults them to empty for older tests.
- **Change requests (story 32) — for story 37:** a change row's `changes` is `{event: [{field, before, after}], spaces: [{space_id, label, fields}]}`; `before` is what the database held when the request was made, at the event `version` the request checked. Applying an approved change must go through one locked function that writes the new values and **bumps `events.version`**, so a stale form can't be resubmitted against it, and should recompute the impact then (CR-R2). Use `change_fields.SIGNIFICANT_*` and the stored `significant` to decide re-review (CR-R5) rather than a second list. Record approvals and rejections on the request row as 115 does; the history already shows `change_requested` and, for superseded rows, `change_request_closed`. Story 112's "Significant changes go through a change request." should read the same `change_fields` sets. `tests/conftest.py::cancellation_requests_offline` also defaults the three change readers to empty.

- **Preparation is an active status (D73).** `ACTIVE_COORDINATOR_STATUSES` (backend and frontend) ends with `preparation`, and tech support's queue (`equipment.service.QUEUE_EVENT_STATUSES`) includes it, so the Requests page keeps linking to the event; that page still opens on "Waiting on you", which hides Reserved lines (D75); any new list of "statuses where the coordinator still works" should include it. Comments (`COMMENTABLE_STATUSES`, `add_event_comment`) still leave it out.
- **Preparation (CR-110, CR-109, 68):** only `private.start_preparation` moves an event into Preparation; call it from your own preparation function after locking the event, so the move, its history and the notices commit together. `events.service.return_to_planning` still ignores Preparation events (DEFECTS D71), so equipment that stops being ready doesn't send a Preparation event back. The organiser's single-event read gets venue and technical preparation info only in Confirmed and Preparation (`_ORGANISER_ARRANGEMENT_STATUSES`).

A `re_review` booking can now be approved or rejected by venue staff; anything else that reads `re_review` as "can't be decided" is out of date.

Show `booked_period` to people and count hold expiry to it; compare `occupied_period` for overlaps and flags. The flag, reason and time are all present or all null. Story 68 AC8 must add `preparation` to `approved_change` when the status exists; the current confirmed-only sources are pinned by a test and TODO. Neither is implemented by CR-104.
- **A block flags in the database, not in Python (CR-95).** `venue_blocks_flag_bookings` fires on insert and on a change to the period or venue, whoever writes the block, and calls `flag_venue_bookings` with `affected`; SCRUM-51's block endpoint does not flag again and does not call `return_to_planning` (flagging leaves the event's status alone, AC7). - **A replacement sits beside the affected or Safety-rejected booking (CR-95).** The affected or Safety-rejected booking is never cancelled, so it stays `held`/`approved` until the replacement is approved and `release_replaced_booking` releases it. The request functions ignore it for the one request that names it in `p_replaces_booking_id`; a plain request is still refused as `already_booked`, and the per-space unique index skips affected or Safety-rejected bookings. Anything that counts "the event's venue" must decide whether an affected or Safety-rejected booking and its replacement are one venue or two: the dashboard readiness treats an affected or Safety-rejected booking as `issue`, and `active_bookings_for_event` lists both.
- **`POST /venue-bookings` with `replaces_booking_id` changes the event's status before it books (CR-95 AC7).** The booking functions accept only a planning event, so `_prepare_replacement` validates the link, then calls `return_to_planning(reason_code="arrangement_flagged")` for a Confirmed or Safety-review event, then requests. If the venue they pick is taken, the event is already in planning (REQUIREMENTS §9 item 64). A `return_to_planning` failure (503) leaves nothing requested. Anything else that books for an event outside planning needs the same ordering.
- **The flag and the replacement link are the coordinator's and venue staff's (CR-95).** `events.service.read` blanks `flag`, `flag_reason` and `replaces_booking_id` for an organiser reading a confirmed event; CR-111 gives the organiser their own view of each venue (QA3-53).

**Architecture and conventions**

- **CI runs on every PR into `main`** — `.github/workflows/ci.yml`, two parallel jobs: `backend` (Python 3.11, `pip install -r backend/requirements.txt`, `pytest --cov`) and `frontend` (Node 20, `npm ci`, `npm run test:coverage`, then `cp .env.example .env && npm run build`). **Both fail if line coverage drops below the floor**: backend `fail_under` in `backend/.coveragerc`, frontend `thresholds.lines` in `frontend/vite.config.js`. A story that lowers coverage turns CI red, so cover your new code. `frontend/src/main.js` is the only excluded file; add another only with its reason in `docs/CI.md` §4 item 2. **It needs no repository secrets**, and must stay that way: the backend suite injects fake Supabase credentials in `backend/tests/conftest.py`, and the build reads the committed placeholders in `frontend/.env.example`. If you add a test that needs real Supabase credentials, it will pass locally and fail in CI — put it behind a marker rather than adding a secret. What CI does *not* check: `ruff` (never run over this codebase), whether a PR's own changed lines are covered (only the totals are), the ADR structural rules, and anything requiring a real database or browser. **Full reference: [`docs/CI.md`](CI.md)**, including what is left to build and when.
- **Test dates must be relative to now when the code compares them with the clock.** Submission rejects an event dated today or earlier, so a fixed date passes until that day and then fails, as D25 did. Build such dates from `datetime.now(...) + timedelta(...)` (see `EVENT_DAY` in `tests/test_events_api.py`); keep fixed dates only for values that are meant to be in the past. It happened again as D78 (CI red from 1 Nov). Two other patterns are safe: in Vitest, fix the clock before the fixtures (`vi.useFakeTimers({ toFake: ["Date"] })` + `vi.setSystemTime(...)`, as `EventRequestView.spec.js` does); in pytest, put a fixed future date in 2099, which shares 2026's calendar (`FUTURE_START` in `tests/test_event_change_decision_api.py`). To check a suite, run it with the clock moved forward a few weeks: a Vitest `setupFiles` entry that replaces `Date` with a shifted subclass, or a pytest plugin that starts `time_machine.travel(now + offset, tick=True)` (how D78's later failures were found; neither is in the repo).
- **Live checks run locally against the real system, not in CI.** `backend/scripts/verify_live.py` sends real requests for the API-shaped cases (login, tokens, role gates, active-role switching) and runs the rolled-back `supabase/verification/*.sql` scripts through `supabase db query`. `frontend/e2e/*.e2e.js` (Playwright, `npm run test:e2e`) drives a real browser through sign-in, session renewal, logout, route guards and the role switcher. Both sign in as the seeded accounts, never change seeded or shared data, and log out every session they open. A check that must create a record makes a throwaway one carrying its run's ID (`live-check+<run>-…@connectsphere.dev` accounts; `live-check <run> …` events, venues and equipment; blocks noted `live-check <run>`). Each run deletes only its own, cascading to everything they own, plus any older than `STALE_AFTER` (6 hours) that a stopped run left, so concurrent runs can't delete each other's rows. Reuse that pattern: name the record with the run's ID (`ctx.run_id` in `verify_live.py`, `RUN_ID` in `e2e/support/throwaway.js`) and add its delete through `mine_or_stale` / `mineOrStale`. A check that would approve, reject or change a shared record stays manual. Name every check with its case ID first (`TC-AUTH-006 …`), since that is how the run log and `grep` find it. With `--record` / `npm run test:e2e:record`, each run writes a log to `docs/test-cases/runs/`. CI's pytest and Vitest jobs upload a JUnit report per run (artifacts, 90 days). Spec files end in `.e2e.js` so Vitest never collects them.

No ORM and no direct Postgres connection: modules read through their `repository.py`, which uses the factories in `app/db/supabase.py`. `app/db/session.py` is now just a re-export of those factories, not a seam for direct SQL. `DATABASE_URL` is an operator convenience for `psql`, seeding and the verification scripts; no application code reads it. The dashboard's affected-replacement list cuts off at the booked end on purpose: once the event is over there is nothing to replace. `parse_occupied_datetime` bounds BCE/five-digit endpoints for application comparisons, and extreme windows are labelled “beyond supported dates”; exact buffers/ranges stay in Postgres. The old `TURNAROUND_MINUTES` constant and `formatTurnaround` wording are removed.

- **History is append-only (story 62 AC6).** A direct UPDATE or DELETE on any of the 8 history tables fails with `55000`, from the API, a function or the SQL editor; a decided `event_change_requests` row is history too, so only update an `open` one. Foreign-key cascades and `on delete set null` still work. A test-fixture reset that must clear history sets `set local connectsphere.history_maintenance = 'on'` in its own transaction (`event_review_fixture_reset.sql`).

- **Edit an event's fields through `public.edit_event`, not `update_event`,** once the event has left draft, so the edit and its history save together (ADR-0007, ADR-0008). Pass the fields, the expected version and the statuses the edit is allowed from; story 112's coordinator edits call it (or `private.record_event_edits` from their own function) the same way. A new history source joins `events.service.history()` as a read from its own table, never as a copy (ADR-0008), and needs its kind's fields added to `EventHistoryEntry`'s serializer and a per-role decision.

**Traps already hit**

- **A key handler on a container must not `.prevent` keys meant for its children.** `BauhausCard` once used `@keydown.enter.prevent`, which cancelled every Enter inside every card: forms wouldn't submit, textareas wouldn't take a new line, and buttons wouldn't press (D13). Use `.self` (`@keydown.enter.self.prevent`) or check `event.target` before preventing. jsdom doesn't simulate implicit form submission, so test this by asserting `defaultPrevented` on the child's keydown (see `BauhausCard.spec.js`), not by expecting a submit event.
- **Supabase SDK:** use `create_auth_client()` for sign-in and refresh, and import exceptions from `supabase_auth.errors`, not `gotrue.errors` (`docs/PROJECT_OVERVIEW.md` §5).
- **Endpoints that call Supabase are plain `def`.** supabase-py is synchronous, and `async def` blocks the event loop (DEFECTS D5).
- **A PostgREST embed must name its constraint when the table has two FKs to the same target.** `venue_bookings` points at `venues` twice — `venue_id` and `suggested_venue_id` — so a bare `venues(name)` fails the *whole query* with `PGRST201`. Use `venues!venue_bookings_venue_id_fkey(name)`. Mocked tests cannot catch this; it only appears against a real database (SCRUM-70).
- **A dashboard route under a module with a `/{id}` path must be declared above it.** `/{event_id}` and `/{venue_id}` are typed `UUID`, so a static path declared after them reaches the `{id}` handler and answers **422, not 404** — which reads like a validation bug rather than a missing route. Both `venues/router.py` and `events/router.py` order theirs correctly, and `test_coordinator_dashboard.py` pins the events one.
- **The events module raises its own `HTTPException` subclasses** (`EventNotFoundError`, `EventConflictError` in `events/service.py`) instead of adding them to `app/core/exceptions.py`, which is what `backend/AGENTS.md` asks for. Follow the core-exceptions rule in new modules; folding these two in is a small cleanup nobody has done yet.
- **An event owned by someone else answers 404, not 403.** `events.service._owned_event` merges "no such row" with "not yours" on purpose, so the API doesn't confirm an id exists to a stranger. Keep that shape in new ownership-scoped endpoints rather than "helpfully" returning 403.
- **`getEarliestEventDate` exists twice** — in `features/events/timezones.js` and `features/events/dateValidation.js`, with the same name and behaviour. Import from `timezones.js`; the duplicate should go when someone is in there.
- **Mapping a half-open period onto calendar days uses `endsAt − 1ms`.** The last instant inside `[start, end)` is `end − ε`, so a block ending at midnight must not mark that day (§6.14, CAL-R2). `features/venues/calendar.js` does this once — don't re-derive it.
- **Never slice a raw ISO string to get a day key.** The same instant serialises as both `...T16:00:00Z` and `...T00:00:00+08:00`, which slice to different days. Use `singaporeDayKey`, which works from the instant.
- **The venue-staff dashboard payload is upcoming-only**, so its calendar cannot page back before the current month — every earlier month would be empty by construction rather than in fact.
- **The venue calendar (SCRUM-57) shows exactly what `venue_conflicts` returns.** A new kind of occupant (a new occupying status, a new kind of unavailability) must go into `venue_conflicts` and `venues.repository.list_calendar_occupants`, or the calendar shows the venue free while requests are refused. `venue_conflicts` returns no block id, so blocks are read separately by the same overlap; keep the `removed_at` skip in both.
- **`event_name` is real now, but only on the venue profile.** SCRUM-67 fills it through `events.service.names_by_id`; `GET /venues/dashboard/venue-staff` still leaves it null, so that dashboard shows short ids. Filling it there is a two-line change in `venues.service.venue_staff_dashboard` and is the obvious follow-up.
- **Tone → pill class maps are duplicated** in `VenueStaffDashboard.vue` and `VenueDetailView.vue`. Tailwind's scanner needs static class names, so the duplication is deliberate for now; the third screen that needs status pills should extract a `BauhausPill` into `components/common/` and take both with it.
- **`tzdata` is a runtime dependency.** `events/schemas.py` validates timezones with `zoneinfo`, which needs a timezone database; Windows has none, so `tzdata` is pinned in `requirements.txt`. Run `pip install -r requirements.txt` again after pulling, or 14 event tests fail with "must be a valid IANA timezone".
- **RLS policies must not query their own table.** It recurses (`42P17`), so use `private.current_user_role()`.
- **The live migration history has drifted from the files before.** Run `supabase migration list --linked` before every `supabase db push` (DEFECTS D8, migration drift).
- **A failed history refresh after a successful approve/reject must not report the decision as failed.** `eventReviewStore.act` (SCRUM-34/52) applies the approve/reject result first and only then reloads history in a separate try; if that reload fails, the previous history stays on screen and the store still reports success — otherwise a coordinator would see "Reject failed" for a rejection that actually went through.
- **`frontend/src/router/__tests__/activeRoleAccess.spec.js` now needs a 20s test timeout,** not Vitest's 5s default. The route matrix test itself runs in ~2.3s alone, but exceeded 5s under full-suite load once SCRUM-34/52's route was added; each new guarded route adds more work to the same test.
- **Never commit `supabase/.temp/` or `supabase/.branches/`.** They're gitignored now. `.temp/` holds generated local secrets, which is how PRs #4 and #6 failed the GitGuardian check.
- **`PATCH /venues/{venue_id}` is a full representation, not a partial patch** — unlike `PATCH /events/{event_id}`'s `exclude_unset` convention. `VenueUpdateRequest` requires every editable field because the edit screen is a pre-filled form submitting the whole record, not a draft autosave; there is no merge-with-current-row step. Don't assume every `PATCH` in this codebase means "send only what changed."

- **Equipment availability has one calculation.** `public.equipment_availability` (worst moment over `[start, end)`, outages and confirmed reservations each at their peak, §6.16) backs the availability check, the windowed inventory and reserving. Don't sum reservations in Python again (D45).
- **The coordinator dashboard's equipment readiness still ignores request lines** (REQUIREMENTS §9 item 17). Now that lines exist, §6.6's "every request `reserved`" can replace the "any reservation" assumption in `events.service._equipment_readiness`.
- **No equipment request notifications.** §6.15 asks for tech support to be told of new lines; SCRUM-45 left it out of scope. Insert into `notifications` inside `submit_equipment_request` (as `request_venue_booking` does on SCRUM-19) when it is picked up.

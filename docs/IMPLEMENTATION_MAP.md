## 2. Backend (`backend/app/`)

### Endpoints (all under `/api/v1`)

| Method and path | Guard | What it does |
|---|---|---|
| `POST /auth/signup` | public | Creates an Event Organiser account that can log in immediately (SCRUM-80). 201 with the profile; 409 if the email has an account; 422 per field, including any role but `event_organiser` (SCRUM-83 adds `attendee`) |
| `POST /auth/login` | public | Signs in and returns tokens and profile (`role` = this session's active role, `roles` = every role the account holds) |
| `POST /auth/refresh` | public (refresh token) | Rotates the session |
| `GET /auth/me` | authenticated | Returns the current user's profile, including `roles` |
| `POST /auth/active-role` | authenticated | Switches the caller's session to a role it holds (SCRUM-75); 403 if the role isn't in `user_roles` |
| `POST /auth/logout` | authenticated | Revokes only the caller's session |
| `GET /venues` | `event_coordinator`, `venue_staff` | Searches the catalogue. Each criterion is strict. `starts_at`/`ends_at` adds an availability check, and `include_excluded=true` also returns ruled-out venues with reasons |
| `GET /venues/{venue_id}` | `event_coordinator`, `venue_staff` | The full venue profile in one response (SCRUM-67): catalogue attributes, `updated_at` + `updated_by` (`{id, full_name}`, null when unrecorded), `turnaround_minutes` (0, QA-28), `photos` (**always `[]`** — declared, populated by nothing, VC-R8), upcoming blocks, and upcoming occupying bookings each carrying `event_name` |
| `GET /venues/dashboard/venue-staff` | `venue_staff` only | The venue-staff work queue across **every** venue (AUTH-R5): pending holds soonest-expiry first (each with `expires_at`; a hold already past it is left out), bookings in re-review, active and upcoming blocks, and the venue catalogue. Declared **above** `/{venue_id}`, which is typed `UUID` and would answer 422 rather than fall through |
| `PATCH /venues/{venue_id}` | `venue_staff` only | SCRUM-63: body `VenueUpdateRequest` — a full representation (name, location, capacity, `layouts`, `facilities`, `accessibility_features`, `opens_at`, `closes_at`, `description`, `confirm`), not a partial patch. Returns `VenueUpdateResponse {saved, venue, warnings}`. If the new attributes newly break an upcoming `held`/`approved`/`re_review` booking's event (VC-R2: capacity vs expected attendance, a dropped required facility or layout, hours that no longer cover the booking) and `confirm` isn't `true`, `saved` is `false` and nothing is written — the SPA shows `warnings` and resubmits with `confirm: true` to proceed. On save, each affected event's coordinator gets a `venue_updated_affects_booking` notification and the edit is recorded in `venue_edit_history` (VC-R3). 404 unknown venue; 422 `closes_at <= opens_at`; 409 "This venue was updated by someone else. Reload." on a lost `venues.version` race (DB-5) |
| `GET /venues/{venue_id}/history` | `event_coordinator`, `venue_staff` | SCRUM-63 (VC-R3): every saved edit to the venue, newest first, as `{entries: [{id, actor: {id, full_name} or null, before, after, at}]}` — `before`/`after` are the full editable-field snapshot, not a per-field diff (the SPA reduces to changed fields) |
| `POST /venue-bookings` | `event_coordinator` (the event's assigned one) | SCRUM-19: body `VenueBookingCreate {event_id, venue_id, note?}` (note trimmed, blank → null, ≤ 1000 chars). **No period in the body:** the hold covers the event's own `[starts_at, ends_at)`. 201 `VenueBooking {id, event_id, venue_id, status: "held", note}`. Through `request_venue_booking`; 409 "Venue already held for this time by another event." / "Venue blocked for this time." / "This event already has a venue booking." / "Requirements are still being amended." / "This event has no start and end time to hold a venue for." / "Cannot request a venue for an event that is <status>."; 403 if not the assigned coordinator (also re-checked under the lock); 404 for a draft or missing event or an unknown venue. Router `venues.router.bookings_router`, mounted in `main.py` |
| `PATCH /venue-bookings/{booking_id}/expiry` | `venue_staff` only (any of them, AUTH-R5) | CR-99 AC2: body `HoldExpiryUpdate {expires_at}` (must carry an offset; a naive time is 422). 200 `HoldExpiry {id, status: "held", expires_at}`. Through `set_venue_hold_expiry`, which records an `expiry_changed` history row and clears the 24-hour-warning marker. 404 "Booking not found."; 409 "This hold has already expired." / "Only a held booking has an expiry to change."; 422 "The new expiry must be in the future." / "The new expiry can't be after the event starts." |
| `POST /events` | `event_organiser` | Creates a draft. Every field is optional at draft stage; the organiser is taken from the JWT, never the body |
| `GET /events` | `event_organiser` | The caller's own events only (`service.list_owned`) |
| `GET /events/dashboard/coordinator` | `event_coordinator` | SCRUM-72: `{action_items, active_events}` for the caller's assigned events in `under_review`/`returned`/`planning`/`safety_review`/`confirmed` (never drafts). Kinds produced: `awaiting_review`, `resubmitted`, `arrangement_issue` (technical readiness `issue`); readiness per event `{venue, equipment, technical}`. Nothing about unassigned events: those are the Event Coordinator Lead's queue (REQUIREMENTS §6.5). Unordered: the SPA ranks. Declared **above** `/{event_id}` (typed UUID, which would answer 422). Two **[Assumption]**s, REQUIREMENTS §6.21.1 |

Call it after changing your own records (flagged/cancelled booking or cleared exit check). `reason_code` is `arrangement_flagged` (CR-94/95), `booking_cancelled` (85), `technical_not_ready` (24), or `approved_details_changed` (37). Free-form `message` is accepted only for caller audit context, never stored or notified; `actor_id` is accepted for interface stability but ignored by the system RPC. The withdrawal has no officer comment or decider. If Supabase is unreachable it raises `EventServiceUnavailableError` (HTTP 503) rather than returning `None`; call it after your own change has committed and decide whether your caller should catch that error (a failed call leaves the event where it was). ## 5. Know before you build

**Architecture and conventions**

- **CI runs on every PR into `main`** — `.github/workflows/ci.yml`, two parallel jobs: `backend` (Python 3.11, `pip install -r backend/requirements.txt`, `pytest --cov`) and `frontend` (Node 20, `npm ci`, `npm run test:coverage`, then `cp .env.example .env && npm run build`). **Both fail if line coverage drops below the floor**: backend `fail_under` in `backend/.coveragerc`, frontend `thresholds.lines` in `frontend/vite.config.js`. A story that lowers coverage turns CI red, so cover your new code. `frontend/src/main.js` is the only excluded file; add another only with its reason in `docs/CI.md` §4 item 2. **It needs no repository secrets**, and must stay that way: the backend suite injects fake Supabase credentials in `backend/tests/conftest.py`, and the build reads the committed placeholders in `frontend/.env.example`. If you add a test that needs real Supabase credentials, it will pass locally and fail in CI — put it behind a marker rather than adding a secret. What CI does *not* check: `ruff` (never run over this codebase), whether a PR's own changed lines are covered (only the totals are), the ADR structural rules, and anything requiring a real database or browser. **Full reference: [`docs/CI.md`](CI.md)**, including what is left to build and when.
- **Test dates must be relative to now when the code compares them with the clock.** Submission rejects an event dated today or earlier, so a fixed date passes until that day and then fails, as D25 did. Build such dates from `datetime.now(...) + timedelta(...)` (see `EVENT_DAY` in `tests/test_events_api.py`); keep fixed dates only for values that are meant to be in the past.
- **Live checks run locally against the real system, not in CI.** `backend/scripts/verify_live.py` sends real requests for the API-shaped cases (login, tokens, role gates, active-role switching) and runs the rolled-back `supabase/verification/*.sql` scripts through `supabase db query`. `frontend/e2e/*.e2e.js` (Playwright, `npm run test:e2e`) drives a real browser through sign-in, session renewal, logout, route guards and the role switcher. Both sign in as the seeded accounts, never change seeded or shared data, and log out every session they open. The sign-up checks create throwaway `live-check+…@connectsphere.dev` accounts, deleted (cascading to everything they own) before and after each run; reuse that pattern for any check that must create a record. A check that would approve, reject or change a shared record stays manual. Name every check with its case ID first (`TC-AUTH-006 …`), since that is how the run log and `grep` find it. With `--record` / `npm run test:e2e:record`, each run writes a log to `docs/test-cases/runs/`. CI's pytest and Vitest jobs upload a JUnit report per run (artifacts, 90 days). Spec files end in `.e2e.js` so Vitest never collects them.

- **Data access is through the Supabase client only** — settled, see [ADR-0002](adr/0002-supabase-client-only-data-access.md). No ORM and no direct Postgres connection: modules read through their `repository.py`, which uses the factories in `app/db/supabase.py`. `app/db/session.py` is now just a re-export of those factories, not a seam for direct SQL. `DATABASE_URL` is an operator convenience for `psql`, seeding and the verification scripts; no application code reads it. This is not a ban on SQL — the integrity guarantees (`DB-1`, and `register_attendee`/`reserve_equipment` for `DB-3`/`DB-4`) belong in the database, and the app will reach the latter two through `.rpc()` when they are built.
- **Occupied periods are half-open `[starts_at, ends_at)`.** A booking ending at 12:00 doesn't conflict with one starting at 12:00. Double-booking is prevented in the database by `venue_bookings_no_overlap`, not by application checks. Terms like Hold, Block, Availability, and Suitability are defined in `CONTEXT.md`.
- **Reuse the venue enums** (`venue_layout`, `facility`, `accessibility_feature`) in any new table that describes event requirements. Don't define parallel ones.
- **Safety review status lists (SCRUM-82):** coordinator active statuses, technical arrangement issues and readiness gaps, comments (backend/frontend/RPC), organiser groups/counts, and the tech-support pending queue include it. Equipment/venue requests remain Planning-only; coordinator rejection excludes Safety review.
- **Readiness check-then-act race:** booking/equipment changes do not bump `events.version`; an arrangement can become unready between the Python check and RPC. The agreed recovery is CR-104 AC10 `safety_withdraw` back to Planning; that recovery is not implemented by 82.
- **Story 84:** Safety review is not yet a cancellation source; decide it explicitly when implementing cancellation.
- **Booking flags:** `BookingReadiness.flags` accepts `affected`, `conflict`, `unsuitable`, `expired`; production supplies empty flags until CR-94/95/99 add them. Every active booking is checked, supporting CR-97's future multiple bookings.
- **Technical status / story 24:** `events.service.technical_status(row) -> ReadinessState` is the single reader for readiness and the coordinator dashboard. Nothing writes `events.technical_readiness` yet; its default is Not required. Eileen replaces the function body to derive status from lines; send her spec §9 (agreement pending).
- **Reusable safety rule:** `events/readiness.py.safety_readiness(bookings, technical) -> SafetyReadiness`; at least one active booking, all approved/unflagged, technical Ready/Not required. Both coordinator GET and POST share it.
- **Notification:** `event_sent_for_safety_check` goes to organiser via `transition_event` and every Safety Officer role holder except the actor via `send_event_to_safety_review`. Held roles only select recipients, never grant access. Notification read UI remains story 53/69.
- **Dashboard summary tiles (D20/D21):** reuse `BauhausSummaryCard` for headings, figures and optional details. Direct grid children stretch automatically; when wrapped in a link, the card uses `h-full`. Grids use base/md/xl for one/two/three-or-four columns, leaving room for the sidebar. Shared `BauhausCard` is unchanged. Browser checks: `dashboard-summary-layout.e2e.js` plus `venue-dashboard-layout.e2e.js`. Tech-support inventory filters still overflow the page at 768px (D22); the summary row itself fits.
- **Two dashboards are fully data-driven: venue staff (SCRUM-70) and coordinator (SCRUM-72).** Tech support and attendee are still shells with hardcoded metrics (DEFECTS D8, the *fabricated-metrics* one). Follow their pattern, and never hardcode a metric. The coordinator dashboard never produces change/cancellation, booking/equipment-decision or re-review action kinds: the stories that build that data must add them to `events.service.coordinator_dashboard` (the SPA already renders every kind in `ACTION_KINDS`).
- **Frontend domain stores go in `features/<domain>/`** (team decision, `frontend/AGENTS.md` "Where stores go"). A domain with more than one store names each file after the store (`venueSearchStore.js`, `venueStaffDashboardStore.js`). **One store still breaks this rule:** `stores/events.js` is a domain store sitting in the app-wide folder. It arrived with SCRUM-8 and is recorded as a follow-up under DEFECTS D9 — don't cite `stores/` as an example of the convention, and move it when you next touch SCRUM-8's screens.
- **Two different defects are both numbered D8** in `DEFECTS.md` (migration drift, and fabricated dashboard metrics); the numbering note at the top of that file explains why they weren't renumbered. When citing D8 anywhere, say which one.
- **Authorise by the session's active role, everywhere (SCRUM-76, `AGENTS.md` security baseline).** API: `require_roles` / `CurrentUser.role`. RLS: `private.current_user_role()`. Frontend: `authStore.role` in `meta.allowedRoles`. Never gate on `user_roles`, `CurrentUser.roles` or `profiles.role`. Two matrix tests iterate every route automatically: a new endpoint with no `require_roles` fails `test_every_protected_endpoint_names_the_roles_it_allows`, and a new guarded route is covered by `activeRoleAccess.spec.js` (a route with no `allowedRoles` fails it unless it is `login` or `profile`).
- **Every lifecycle transition must go through `transition_event` and a `lifecycle.TRANSITIONS` row** (SCRUM-34/52). SCRUM-12 (auto-assignment, `submitted → under_review`) and SCRUM-33 (return/resubmit) must add rows to `lifecycle.TRANSITIONS` and call `transition_event`, not write `events.status` directly — the RPC's history write, the version check, and the notification are otherwise silently skipped. Submission (`draft → under_review`, `TRANSITIONS["submit"]`) follows this rule since D11. **Creation is the one history row not written by `transition_event`:** the `events_record_created` trigger writes it, so any insert into `events` — API, seed or fixture — starts the event's history. A seed or fixture that inserts an event directly in a later status gets a `(none → <that status>)` row and nothing in between; that's expected for fixtures.
- **`transition_event` does not re-check `coordinator_id`.** The assigned-coordinator check (`service._assigned_event`) happens before the RPC is called, not inside it — the RPC only enforces `status = any(from_statuses)` and `version = expected_version`. That stays a safe substitute only as long as *every* write to `events` bumps `version`, since a stale caller's request would otherwise still match. SCRUM-12's reassignment (changing `coordinator_id`) must bump `version` too, or a request built against the old assignment could still land.
- **A coordinator who isn't assigned gets 403, not 404,** on `GET/POST /events/{id}[/approve|/reject|/history]` (SCRUM-34/52 AC3) on non-draft events. This deliberately departs from the organiser's "404, not 403" shape (§2): coordinators may already search every non-draft event (QA-87), so confirming an id exists reveals nothing a coordinator couldn't already find. A `draft` answers 404 to every coordinator, assigned or not, on all four routes (`service._assigned_event`), because drafts are private to their organiser (DR-R2, QA2-16).
- **`notifications` is written but has no read API or bell yet** (SCRUM-27: 69, 53). Types written so far: `event_sent_for_safety_check` (organiser and Safety Officers, SCRUM-82), `event_approved`, `event_rejected`, `event_returned` (to the organiser), `event_resubmitted` (to the coordinator, SCRUM-33), `comment_added` (to the other party, SCRUM-61) and `venue_booking_requested` (to every `venue_staff` holder except the requester, SCRUM-19), with nothing in the UI to show them.
- **Booking requests decide every refusal in the database** (SCRUM-19). `request_venue_booking` locks the event, re-checks status and assignment, checks blocks, and lets `venue_bookings_no_overlap` (DB-1) and `venue_bookings_one_active_per_event` (BR-R1) settle overlaps and races, returning an outcome code instead of raising. Don't add a "is it free?" query in Python before calling it: that check-then-insert races. A `returned` event is refused with "Requirements are still being amended." (BR-R6).
- **SCRUM-19 doesn't check suitability.** A coordinator can request a venue whose capacity or facilities don't fit; the search shows those reasons but the request doesn't refuse them. SCRUM-18 owns the suitability verdict and should call it from `venues.service.request_booking` before the RPC (BR-R3).
- **There is no way to cancel a booking yet** (BR-R5, SCRUM-85). Throwaway bookings made by tests are deleted directly in SQL; see `verify_live.py`'s `delete_throwaway_bookings`.
- **The venue-staff request page (`/bookings/:id`) is still a stub.** The request's note (`venue_bookings.request_note`) and requester (`requested_by`) are stored but not shown anywhere yet; SCRUM-20/36 should show them there.
- **`EventRequestView` always reads `?id=` with `eventsStore.get(id)`**, never the cached list (a stale list once left a blank form whose Save draft created a duplicate). Amend mode is keyed on `form.status === "returned"`; a status other than `draft`/`returned` redirects to `/events/:id`. The amendment only arrives through the single-event read (the list endpoint leaves it `null`).
- **Editing payloads send `null` for emptied fields** (`eventToPayload(…, { clearing: true })`, D12). A new edit path must do the same, or clearing a field silently keeps the old value.
- **The coordinator review page is opened from the coordinator dashboard** (`/coordinator/events/:id`). `CoordinatorEventView` reactively reloads on in-place param changes via `watch(() => route.params.id)`. Its parallel first requests are where DEFECTS **D18** showed up (fixed).
- **Equipment reservations are not released on rejection yet** — `transition_event` releases `venue_bookings` but has only a documented hook for equipment, because SCRUM-24's reservation flow isn't built.
- **Fixture events `e0000000-…-0201` and `e0000000-…-0202`** (with booking `d0000000-…-0201`) exist in `supabase/seed.sql` for review testing (SCRUM-34/52) — see §4.
- **The coordinator's approve toast reads "Request moved to Planning", never "approved"** — consistent with the rule in §5/REQUIREMENTS §5 that only `confirmed` is described as "approved" (QA2-8).
- **`BauhausCard background="red"` is only a ~4px accent stripe in the browser, not a filled red card.** The organiser's rejection notice therefore uses the page's own alert tokens (solid red block, white text) instead of `BauhausCard`. If a future screen needs an unmistakably urgent card, don't assume `background="red"` alone reads as urgent — check it visually first. The same holds for `blue` and `yellow`: the card's surface is always white, so never put white (`text-canvas`) text inside a toned `BauhausCard` — the organiser's Registration card did, and its labels vanished (D23). `VenueSearchView`'s booking-context card still carries a dead `text-canvas` class that the card's own `text-ink` overrides; it reads correctly, but don't copy it.
- **Before merging the unmerged dashboard branches** (SCRUM-71 organiser dashboard, SCRUM-73 tech-support dashboard with its `equipment` endpoints): re-check that each new endpoint uses `require_roles` and each new route sets `allowedRoles`. The matrix tests will flag a gap, but only once the branch is merged with this one. Their acceptance criteria also assume one dashboard per login, which no longer holds once the active role can differ from the default; that revisit was deferred until the branches merge.

- **Holds expire (CR-99).** A `held` booking always has `expires_at`; the `expire-venue-holds` pg_cron job flips overdue ones to `expired` every minute and notifies the coordinator. A new path that inserts a hold gets its default expiry from the trigger, but must call `public.expire_venue_holds()` before its overlap check, or a hold up to a minute past its expiry still blocks it. CR-98's `request_venue_booking_for_space` (live, not on `main`) does not do this yet.

Seeded hold `…0002`'s event was 10 Oct 2026, so it expired on the job's first run on the live project.

**Traps already hit**

- **A key handler on a container must not `.prevent` keys meant for its children.** `BauhausCard` once used `@keydown.enter.prevent`, which cancelled every Enter inside every card: forms wouldn't submit, textareas wouldn't take a new line, and buttons wouldn't press (D13). Use `.self` (`@keydown.enter.self.prevent`) or check `event.target` before preventing. jsdom doesn't simulate implicit form submission, so test this by asserting `defaultPrevented` on the child's keydown (see `BauhausCard.spec.js`), not by expecting a submit event.
- **Supabase SDK:** use `create_auth_client()` for sign-in and refresh, and import exceptions from `supabase_auth.errors`, not `gotrue.errors` (`docs/PROJECT_OVERVIEW.md` §5).
- **Endpoints that call Supabase are plain `def`.** supabase-py is synchronous, and `async def` blocks the event loop (DEFECTS D5).
- **A PostgREST embed must name its constraint when the table has two FKs to the same target.** `venue_bookings` points at `venues` twice — `venue_id` and `suggested_venue_id` — so a bare `venues(name)` fails the *whole query* with `PGRST201`. Use `venues!venue_bookings_venue_id_fkey(name)`. Mocked tests cannot catch this; it only appears against a real database (SCRUM-70).
- **A dashboard route under a module with a `/{id}` path must be declared above it.** `/{event_id}` and `/{venue_id}` are typed `UUID`, so a static path declared after them reaches the `{id}` handler and answers **422, not 404** — which reads like a validation bug rather than a missing route. Both `venues/router.py` and `events/router.py` order theirs correctly, and `test_coordinator_dashboard.py` pins the events one.
- **The events module raises its own `HTTPException` subclasses** (`EventNotFoundError`, `EventConflictError` in `events/service.py`) instead of adding them to `app/core/exceptions.py`, which is what `backend/AGENTS.md` asks for. Follow the core-exceptions rule in new modules; folding these two in is a small cleanup nobody has done yet.
- **An event owned by someone else answers 404, not 403.** `events.service._owned_event` merges "no such row" with "not yours" on purpose, so the API doesn't confirm an id exists to a stranger. Keep that shape in new ownership-scoped endpoints rather than "helpfully" returning 403.
- **`getEarliestEventDate` exists twice** — in `features/events/timezones.js` and `features/events/dateValidation.js`, with the same name and behaviour. Import from `timezones.js`; the duplicate should go when someone is in there.
- **Mapping a half-open period onto calendar days uses `endsAt − 1ms`.** The last instant inside `[start, end)` is `end − ε`, so a block ending at midnight must not mark that day (§6.14, CAL-R2). `features/venues/calendar.js` does this once — don't re-derive it.
- **Never slice a raw ISO string to get a day key.** The same instant serialises as both `...T16:00:00Z` and `...T00:00:00+08:00`, which slice to different days. Use `singaporeDayKey`, which works from the instant.
- **The venue-staff dashboard payload is upcoming-only**, so its calendar cannot page back before the current month — every earlier month would be empty by construction rather than in fact.
- **`event_name` is real now, but only on the venue profile.** SCRUM-67 fills it through `events.service.names_by_id`; `GET /venues/dashboard/venue-staff` still leaves it null, so that dashboard shows short ids. Filling it there is a two-line change in `venues.service.venue_staff_dashboard` and is the obvious follow-up.
- **Tone → pill class maps are duplicated** in `VenueStaffDashboard.vue` and `VenueDetailView.vue`. Tailwind's scanner needs static class names, so the duplication is deliberate for now; the third screen that needs status pills should extract a `BauhausPill` into `components/common/` and take both with it.
- **`tzdata` is a runtime dependency.** `events/schemas.py` validates timezones with `zoneinfo`, which needs a timezone database; Windows has none, so `tzdata` is pinned in `requirements.txt`. Run `pip install -r requirements.txt` again after pulling, or 14 event tests fail with "must be a valid IANA timezone".
- **RLS policies must not query their own table.** It recurses (`42P17`), so use `private.current_user_role()`.
- **The live migration history has drifted from the files before.** Run `supabase migration list --linked` before every `supabase db push` (DEFECTS D8, migration drift).
- **A failed history refresh after a successful approve/reject must not report the decision as failed.** `eventReviewStore.act` (SCRUM-34/52) applies the approve/reject result first and only then reloads history in a separate try; if that reload fails, the previous history stays on screen and the store still reports success — otherwise a coordinator would see "Reject failed" for a rejection that actually went through.
- **`frontend/src/router/__tests__/activeRoleAccess.spec.js` now needs a 20s test timeout,** not Vitest's 5s default. The route matrix test itself runs in ~2.3s alone, but exceeded 5s under full-suite load once SCRUM-34/52's route was added; each new guarded route adds more work to the same test.
- **Never commit `supabase/.temp/` or `supabase/.branches/`.** They're gitignored now. `.temp/` holds generated local secrets, which is how PRs #4 and #6 failed the GitGuardian check.
- **`PATCH /venues/{venue_id}` is a full representation, not a partial patch** — unlike `PATCH /events/{event_id}`'s `exclude_unset` convention. `VenueUpdateRequest` requires every editable field because the edit screen is a pre-filled form submitting the whole record, not a draft autosave; there is no merge-with-current-row step. Don't assume every `PATCH` in this codebase means "send only what changed."

- **Equipment request lines are `pending` only.** Nothing reserves, rejects or releases them yet (SCRUM-24). `transition_event` doesn't release lines on rejection either; `pending_queue` hides lines on closed events instead.
- **The coordinator dashboard's equipment readiness still ignores request lines** (REQUIREMENTS §9 item 17). Now that lines exist, §6.6's "every request `reserved`" can replace the "any reservation" assumption in `events.service._equipment_readiness`.
- **No equipment request notifications.** §6.15 asks for tech support to be told of new lines; SCRUM-45 left it out of scope. Insert into `notifications` inside `submit_equipment_request` (as `request_venue_booking` does on SCRUM-19) when it is picked up.

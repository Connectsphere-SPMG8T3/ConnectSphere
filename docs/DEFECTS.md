# ConnectSphere — Defects

**Every known defect, its evidence, and whether it is fixed.** Edited in place: when a defect is fixed or accepted, update its row.

- Add a new defect as the next number (after **D17**, that is **D18**), with the date and branch it was found on. A fix branch updates the defect's row and adds a [`BUILD_LOG.md`](BUILD_LOG.md) entry with the reproduction, root cause and verification.
- Cite a defect as "DEFECTS D<n>". D1–D16 were first recorded in `docs/PROJECT_REVIEW.md` §A2 (split out on 2026-09-28), so "PROJECT_REVIEW D<n>" in older commits, Jira comments and log entries is the same defect.

> **Numbering note:** two different defects were both filed as **D8** (migration drift, and fabricated dashboard metrics). Both are kept as written rather than renumbered, since they are cited by those names elsewhere in the docs; tell them apart by name ("D8, migration drift" / "D8, fabricated metrics").

> **Status (13 Sep 2026):** D1–D6 are **fixed** on branch `fix/auth-security-bugs`. The database migration `20260913120749` is already applied to the live project. Reproduction, root cause, and verification for each defect are in `docs/BUILD_LOG.md` §4.2. D1 turned out to be broader than first described: the shared client also silently auto-refreshed (and so rotated) the last signed-in user's token. Still open: **D7** (SCRUM-50 `communication_preferences` column, left to the story owner) and the leaked-password-protection dashboard toggle.

| **D1** | **Critical** | **Logout signs out the wrong user.** `get_supabase_anon_client()` is `@lru_cache`'d, so one client instance is shared by every request. `sign_in_with_password` stores that user's session *inside* the shared client, and `logout()` calls `anon_client.auth.sign_out()`, which revokes the stored session with `scope="global"`. When user A logs out, the session revoked is that of **whoever last logged in through the API** (on all their devices). The `access_token` argument to `service.logout()` is never used. | `backend/app/db/supabase.py:8`, `backend/app/modules/auth/service.py:52-60`; `supabase_auth/_sync/gotrue_client.py:779-798` (sign_out reads `self.get_session()`) | Create a **fresh, non-persisting client per sign-in** (`ClientOptions(persist_session=False, auto_refresh_token=False)`). Log out with `admin_client.auth.admin.sign_out(access_token, "local")`. Add a regression test in which two users log in and one logs out. |
| **D2** | **Critical (security)** | **Anyone can self-register as internal staff.** Sign-up is enabled on the project (`disable_signup=false`), and the `handle_new_user()` trigger copies `raw_user_meta_data->>'role'` into `profiles.role`. | **D16** | Low (accepted risk) | **A rate-limited sign-in is reported as a wrong password.** When Supabase refuses a sign-in because too many came from one IP, GoTrue answers 429, supabase-auth raises it as an `AuthApiError`, and `login` maps every `AuthApiError` to 401 "Invalid email or password." A user with the right password is told it is wrong, and the SPA can't show "try again in a few minutes". The same mapping makes a rate-limited run of the live checks indistinguishable from broken sign-in. TC-AUTH-018 describes the rate limit but never pinned down this message. | Found reading `backend/app/modules/auth/service.py::login` (the `except AuthApiError` branch) while adding rate-limit handling to the live checks, 28 Sep 2026, on `chore/automated-live-checks` | **Accepted for now** (28 Sep 2026).
